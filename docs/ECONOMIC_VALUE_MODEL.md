# Economic value model

This page documents the code in `amperes/economics.py`: `estimate(assumptions, measured)`. The pilot report calls it
from `amperes/pilot_report.py` `build()`. The description matches code digest `4434899c1276c5e9`, the value of
`amperes.provenance.code_digest()` when this page was written. If the code and this page ever disagree, the code is
authoritative and this page is wrong.

**Current result: no value has been computed.**
- The existing pilot report says "No ROI computed: inputs are insufficient." Source:
  `amperes_data/artifacts/reports/pilot/ds_20261029T210352_1e9285/pilot_readiness.md`. That report was generated by
  the final code `4434899c1276c5e9`.
- The current code returns the same statement when it has no study and no assumptions.

Every output carries the label "ESTIMATE — depends on the assumptions shown; not a measured saving".

## 1. Inputs

### 1a. Measured inputs (from `amperes/review.py` `study_report`)

`pilot_report.build()` passes `estimate()` exactly two measured values:

| `measured` key | Where it comes from | Value when there is no study |
|---|---|---|
| `median_time_saved_per_task_s` | `study_report(study_id)["median_time_saved_per_task_s"]`. This is the median `duration_s` of completed condition-A tasks (existing workflow) minus the median of completed condition-B tasks (Amperes-assisted). It is `None` unless both conditions have at least one completed task. | `None` |
| `study_status` | `study_report(...)["status"]`. One of: `"measured"` (at least `MIN_TASKS_PER_CONDITION` = 10 completed tasks in each condition); `"preliminary (fewer than 10 tasks per condition)"`; `"not measured — no completed tasks in one or both conditions"`. | `"no workflow study recorded"` |

How the study measures durations (`amperes/review.py`):
- **Plan.** `study plan <dataset_id> --reviewers r1,r2,...` splits a sample into two halves, `S1` and `S2`. The split
  is stratified by `quality_status` (default `--sample-size 20`, seed 0).
- **Assignment.** Each reviewer does one half under A and the other under B. Condition order alternates AB/BA across
  reviewers. For reviewers where `i % 4 >= 2`, the task sequence is also reversed.
- **Timing.** `study start <task_id>` and `study finish <task_id> --confirmed N --incorrect M` set the duration as
  wall-clock time between start and finish. The CLI does not accept a manual duration.
- **Caveat.** The report states: "Counterbalanced AB/BA order across reviewers; samples are split by quality status.
  Not causal with small n."

The pilot report's `workflow_time` section is classed according to the study status:

| Study status | Class |
|---|---|
| `measured` | `MEASURED` |
| begins with `preliminary` | `MEASURED (PRELIMINARY)` |
| anything else, or no study | `MISSING` |

**Status:** the workflow study has never been run. The `workflow_tasks` table in `amperes_data/amperes.db` is empty,
so no time saving exists.

### 1b. Assumptions (user-supplied JSON file: `pilot-report <ids> --assumptions file.json`)

There are **no defaults**. The numbers in the module docstring are examples only. A missing key makes the line that
needs it `not_computable`. Keys that no formula reads are ignored.

| Key | Used by |
|---|---|
| `engineer_cost_per_hour` | triage savings, operating cost, net value, setup cost |
| `triage_tasks_per_week` | triage savings |
| `weeks_per_year` | triage savings, operating cost, yield line |
| `amperes_operating_hours_per_week` | operating cost and net value (optional) |
| `amperes_setup_hours` | one-time setup cost (optional) |
| `eligible_episodes_per_week` | yield line |
| `target_yield_gain_pp` | yield line (percentage points) |
| `value_per_usable_episode` | yield line |

## 2. Low / central / high rules (`_tri`)

- **Number:** the same value is used for `low`, `central` and `high`.
- **Object:** must contain all three keys `low`, `central` and `high`. Otherwise `ValueError` is raised and the CLI
  exits with code 2.
- **String:** kept as-is, without conversion. If a formula uses it, the arithmetic fails.
- **Absent or `null`:** treated as missing.
- **Measured seconds-saved:** a single number used in all three scenarios. The spread therefore comes only from
  the assumptions.
- **Scenario pairing:** each scenario pairs like with like (low with low, and so on). `low` is a worst case only if
  the user orders every triple that way.

## 3. Formulas (for each scenario s ∈ {low, central, high})

### `direct_triage_time_savings` (kind: "extrapolated from a measured per-task difference")

Computed only when `median_time_saved_per_task_s` is not `None` **and** `engineer_cost_per_hour`,
`triage_tasks_per_week` and `weeks_per_year` are all present. Otherwise it is `not_computable`, with the study
status or the missing keys as the reason.

```
extrapolated_hours_per_year[s]       = saved_s / 3600 × triage_tasks_per_week[s] × weeks_per_year[s]
gross_value_per_year[s]              = extrapolated_hours_per_year[s] × engineer_cost_per_hour[s]
amperes_operating_cost_per_year[s]   = amperes_operating_hours_per_week[s] × weeks_per_year[s] × engineer_cost_per_hour[s]
                                       (null if amperes_operating_hours_per_week is absent)
net_value_per_year[s]                = gross_value_per_year[s] − amperes_operating_cost_per_year[s]
                                       (null if the operating cost is null)
```

Flags on the item:

| Flag | When it is true |
|---|---|
| `preliminary` | `study_status` does not start with `"measured"` |
| `no_saving_measured` | `saved_s <= 0` |

Negative values are **not clipped**: an assisted workflow that is slower produces negative gross and net values.
The one-time setup cost is not netted.

### `potential_yield_increase` (kind: "hypothetical — yield gain is an assumption, not measured")

Needs `eligible_episodes_per_week`, `target_yield_gain_pp`, `value_per_usable_episode` and `weeks_per_year`.

```
value_per_year[s] = eligible_episodes_per_week[s] × target_yield_gain_pp[s] / 100 × weeks_per_year[s] × value_per_usable_episode[s]
```

The measured yield is **not** an input to this formula. For example, the 89.4% (429/480) in
`amperes_data/artifacts/reports/pilot/ds_20261029T210352_1e9285/pilot_readiness.md` plays no part. The gain is
purely assumed. The code attaches the warning "Additional usable episodes do not have a fixed value; this line is the
least reliable."

### `recurring_incident_reduction`

Always `not_computable`. Reason given: "requires a before/after incident-rate comparison over a longer pilot".

### `one_time_setup_cost`

`amperes_setup_hours[s] × engineer_cost_per_hour[s]`. Only produced when both keys are present.

## 4. Double-counting guard

The output carries this string: "By construction: labor savings appear only in direct_triage_time_savings; the
yield line uses value per usable episode and no labor terms. Inputs not used by any formula are ignored."

- **What the code enforces:** the guard holds by construction, because no formula combines the two lines.
- **What it does not check:** what `value_per_usable_episode` represents. Pilot rule: that value must exclude all
  operator and engineer labour. Any total assembled by hand must not add the triage line and the yield line.

## 5. When ROI is refused

The code never computes an ROI ratio or a payback period. `roi_statement` takes one of three forms:

| Computed items | `roi_statement` |
|---|---|
| `direct_triage_time_savings` | "Direct triage value is extrapolated from a measured per-task difference". The qualifier " (PRELIMINARY study)" is added if `preliminary`, and "; the assisted workflow was not faster, so no saving is claimed" if `no_saving_measured`. The statement then ends ". Any yield line is hypothetical." |
| only `potential_yield_increase` | "No measured ROI: only the hypothetical yield line could be computed from assumptions." |
| none | "No ROI computed: inputs are insufficient." (current state) |

**Pilot policy:** quote a triage value externally only when `study_status == "measured"` and `no_saving_measured` is
false. Show a preliminary value only with its PRELIMINARY label.

## 6. Running it in a pilot

```bash
python -m amperes.cli study plan <dataset_id> --reviewers rv1,rv2,rv3,rv4
# each reviewer, per task: study start <task_id> … study finish <task_id> --confirmed N --incorrect M
python -m amperes.cli study report <study_id>
python -m amperes.cli pilot-report <dataset_id> --assumptions customer_assumptions.json --study <study_id> \
    --analysis-config analysis.json
```

Every assumption must come from the customer, in writing, and is reported verbatim under `assumptions`.
