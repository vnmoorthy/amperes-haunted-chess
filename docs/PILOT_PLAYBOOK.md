# Pilot playbook: staged pilot

How to run the pilot, stage by stage. Each stage has an entry condition, the commands, an exit condition, and a
role responsible for it.

- Criteria: [PILOT_ACCEPTANCE_CRITERIA.md](PILOT_ACCEPTANCE_CRITERIA.md)
- Economics: [ECONOMIC_VALUE_MODEL.md](ECONOMIC_VALUE_MODEL.md)
- Formats: [INTEGRATION_GUIDE.md](INTEGRATION_GUIDE.md)
- All commands are `python -m amperes.cli <command>`; they are defined in `amperes/cli_data.py`.
- Nothing here has been run with a customer.

## Stage 0: Scoping and baseline (customer data not yet touched)

- **Entry:** the decision owner names one workflow and one dataset.
- **Do:**
  - Record baseline B1–B4.
  - Agree the thresholds and freeze them in two files.
    - **`rules.json`** allows exactly these keys: `disabled_rules`, `required_metadata`, `min_rows`,
      `end_tolerance_s`, `stream_end_spread_s`, `gap_factor`, `plausible_unix_range`, `saturation_fraction`,
      `shift_min_episodes`, `shift_min_sessions`.
    - **`analysis.json`** allows `usable_statuses`, `rejected_tolerance` (default 0.05) and
      `min_session_episodes` (default 10).
    - An unknown key makes the CLI exit with code 2.
  - Agree the data boundaries: local machine only, a deletion date, who can see reports.
- **Exit:** a signed one-page scope, the two frozen config files, and the baseline.
- **Owner:** customer decision owner and Amperes evaluation lead.

## Stage 1: Mapping and validation (no import)

- **Do:**
  - Customer technical lead and Amperes pilot engineer map the export to the CSV package or JSONL.
  - Write `streams.csv` declarations (rate, valid range, max-unchanged).
  - Map event types to `amperes/ops.py` `EVENT_TYPES`.
- **Commands:**
  - `validate <path>` (exit code 1 if any record is invalid, any event has errors, or any record has dropped rows)
  - `schema`
- **Exit:** criterion C2 met, or every rejection explained and accepted.

## Stage 2: Shadow run

- **Commands:**
  1. `shadow <path> --name <label> --rules-config rules.json`. This imports read-only, records
     `import_report.rule_settings`, builds incidents, writes the report and checks the source fingerprint. The
     shadow report uses the *default* analysis settings and contains no simulator results.
  2. `pilot-report <dataset_id> --analysis-config analysis.json` regenerates the report with the agreed usable
     definition and tolerances, recorded as `analysis_settings`.
  3. For drill-down: `ops metrics|bottlenecks|correlate <dataset_id> --analysis-config analysis.json`. Add
     `[--filter operator_id=… | workcell_id=… | session_id=…]` to narrow the scope. `ops metrics` includes
     `yield_loss_attribution`.
  4. `incidents list <dataset_id>` and `incidents show <id>`.
- **Exit:** `source_unchanged: true`, `robot_commands_issued: 0` (criterion C1), and the report is written to
  `amperes_data/artifacts/reports/pilot/<dataset_id>/`.
- **Synthetic reference run** (`amperes_data/artifacts/reports/pilot/ds_20261029T210352_1e9285/pilot_readiness.md`,
  generated by the final code `4434899c1276c5e9`): 480 episodes imported, 0 rejected, 4 incidents, 15 bottleneck
  findings, `source_unchanged` true.
- **Also in that report:**
  - Yield loss attribution: 51 lost = 43 `event data_recording_failure:CAM_FRAME_DROP` + 8
    `finding C005_missing_outcome`.
  - `B001_high_rejected_share`: 43 rejected, plus 8 suspicious episodes pending review.

## Stage 3: Review

- **Do:**
  - Draw a random, rule-stratified sample of findings. Also draw a random sample of yield-loss attributions for
    criterion C7.
  - Each reviewer runs `review add <finding_id> --decision <d> --reviewer <pseudonym>`. Incidents use
    `--kind incident`.
- **Commands:** `review report <dataset_id>`, which reports `precision_among_reviewed` overall and by rule.
  - `info` notes (`O001_unverified_success`) are excluded from the denominators and counted in
    `info_notes_excluded`. In the synthetic dataset that leaves 56 reviewable findings, with 397 info notes
    excluded (recomputed from `amperes_data/amperes.db`).
  - Recall is never computed from review data.
- **Exit:** measure criteria C3–C7. A rule below the C3 floor goes into `disabled_rules`, then `qc <dataset_id>
  --rules-config rules.json` re-runs the checks.

## Stage 4: Workflow study (needed before any time or ROI statement)

- **Commands:**
  - `study plan <dataset_id> --reviewers rv1,...,rvN`
  - then, per task: `study start <task_id>` → `study finish <task_id> --confirmed N --incorrect M --missing-info "..."`
  - `study report <study_id>`
- **Exit:** status `measured` (≥ 10 completed tasks per condition), shown in the report as workflow time class
  `MEASURED`. If fewer tasks complete, the class is `MEASURED (PRELIMINARY)` and C8 is "not evaluated".

## Stage 5: Report and decision

- **Command:** `pilot-report <dataset_id> --analysis-config analysis.json --assumptions customer_assumptions.json --study <study_id>`
  - Add `--experiment <id>` or `--include-latest-sim` only if simulator evidence is wanted. Otherwise the section
    reads "NOT INCLUDED".
- **Decision meeting:** go through C1–C10 one at a time, each recorded as pass, fail or not evaluated. Possible
  outcomes: continue, extend, or stop.

## Stage 6: Deletion

- **Command:** `delete-dataset <dataset_id> --yes`. This removes:
  - episodes, findings, incidents, events and reviews;
  - `workflow_tasks` rows whose `sample_id` starts with `<dataset_id>:`;
  - the dataset artifact directory, every `reports/pilot/` directory whose name contains the dataset id (single- and
    multi-dataset reports), and the dataset's incident export files.
- **Still delete by hand:** any copies made outside `amperes_data/`.
- **Exit:** criterion C10, with a deletion record signed by both sides.

## Known limitations to disclose at Stage 0

- **Yield-loss attribution is linkage, not root cause.**
  - It prefers a linked event over a finding. An episode with any linked fault, intervention, reset or restart event
    is attributed to that event, even if a finding was the actual reason.
  - Incidents remain separate per rule and per event code. In the synthetic run, `C004_truncated` and
    `CAM_FRAME_DROP` are two incidents over the same 43 episodes; the attribution table is what joins them.
- **Strict verified yield is 0/480 without independent outcome evidence** (`pilot_readiness.json`). Usable yield
  relies on source labels (`valid_success_unverified`).
- **Imported logs are replay class D.** No regression cases can be made from them.
- **Only two adapters exist:** JSONL and the CSV package.

## One-page proposal (hand-out)

**What it is.** A read-only audit of one approved collection export:
- whether each episode is usable, with a failed task counted as usable when its data is valid;
- where each lost episode went, attributed once to a linked operational event or a rule finding, with the
  episode-hours lost;
- which failures recur across sessions.

It runs locally, sends no data off the machine (no model provider ships), and issues no robot commands.

**What it is not.** It is not a monitoring platform, a ticketing system, a dataset format, a root-cause engine, or
evidence that anything transfers from simulation to physical robots.

**Evidence so far (synthetic only).**
- On a planted 3-workcell package, yield was 89.4% (429/480) and all 6 planted patterns surfaced. Sources:
  `amperes_data/artifacts/reports/pilot/ds_20261029T210352_1e9285/pilot_readiness.md` and
  `amperes_data/samples/ops_package/planted_truth.json`.
- Its 51 lost episodes split into 43 linked to camera frame-drop events and 8 with missing outcome labels
  (recomputed with the current code from `amperes_data/amperes.db`).
- On an injected-defect corpus it caught all detectable defects and preserved 40/40 clean episodes. Source:
  `amperes_data/artifacts/reports/detector_eval/detector_eval.md`.
- The same author wrote the rules and the corpora.
- **No time saving has been measured.**

**Pilot.** One workflow, one dataset, 2–4 weeks (proposed), stages 0–6 above, and criteria C1–C10 with thresholds
frozen in config files before we see the data.

**You provide:** the export, stream declarations, baseline B1–B4, 2+ reviewers, and a decision owner.

**We provide:** mapping, runs, report, the study instrument, and deletion.

**Decision.** A meeting at the end, with three outcomes: continue, extend, or stop.

**Price:** a proposal, negotiable (see [PHASE3_PILOT_OFFER.md](PHASE3_PILOT_OFFER.md)).
